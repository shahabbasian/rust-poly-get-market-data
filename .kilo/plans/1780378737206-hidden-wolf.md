# Phase 2: Real-Time Orderbook Deep Collection Plan

## Overview

Phase 1 discovers markets via Gamma API REST and stores them in `new_markets`.
Phase 2 connects to Polymarket Market WebSocket to capture **full-depth orderbook
data** from market start to end, stores the final resolution outcome, and
computes `price_to_beat` from `chainlink_prices`.

**Target:** 7 crypto (btc, eth, sol, xrp, doge, hype, bnb) × 4 timeframes (5m, 15m, 1h, 4h) = up to 28 active markets at a time.

## Detailed Component Design

### 1. `phase2/lifecycle.rs` — Market State Manager

Runs on a `tokio::time::interval` (configurable, default 5s).

**Responsibilities:**
1. Query all markets from `new_markets` where `status IN ('upcoming', 'active')`
2. For each market, determine current status:
   - `start_date <= now()` → transition to `active`
   - `end_date <= now()` OR has `winning_outcome` → transition to `completed`
3. On newly-active market: compute `price_to_beat` from `chainlink_prices`
4. Return a `Vec<MarketRecord>` of markets that need WebSocket subscription
   (active markets + upcoming markets starting within next 60 seconds)
5. On `market_resolved` event from WebSocket: set `winning_outcome`, `status='completed'`

**`price_to_beat` logic:**
- Map symbol to chainlink symbol: `btc`→`btc/usd`, `eth`→`eth/usd`, etc.
- Query: `SELECT price FROM chainlink_prices WHERE symbol = $1 AND timestamp >= $2 ORDER BY timestamp ASC LIMIT 1`
  (find the first chainlink price AT or AFTER market start_date; chainlink timestamp is unix milliseconds)
- Falls back to the closest price within ±60s of start_date if no exact match

```rust
pub struct MarketState {
    pub status: &'static str,      // "upcoming" | "active" | "completed"
    pub price_to_beat: Option<f64>,
}

pub async fn refresh_market_states(pool: &PgPool) -> Vec<(MarketRecord, MarketState)>;
pub async fn compute_price_to_beat(pool: &PgPool, symbol: &str, start_date: DateTime<Utc>) -> Option<f64>;
pub async fn transition_status(pool: &PgPool, token_id_yes: &str, new_status: &str) -> Result<()>;
pub async fn set_winning_outcome(pool: &PgPool, token_id_yes: &str, outcome: &str) -> Result<()>;
```

### 2. `phase2/ws_manager.rs` — WebSocket Client

Wraps `polymarket_client_sdk_v2::clob::ws::Client`.

**Connect & subscribe flow:**
1. Create `Client::default()`
2. Call `subscribe_orderbook(asset_ids)` with all active-market token IDs (both Yes and No)
3. The SDK handles heartbeats (PING every 10s) and reconnection automatically
4. The SDK's `OrderBookSnapshot` struct contains `asset_id`, `market` (condition_id), `bids: Vec<Level>`, `asks: Vec<Level>`, `timestamp`, `hash`

**Dynamic subscription strategy:**
When `lifecycle` detects new markets that need watching:
1. Drop the current stream
2. Re-create with updated `asset_ids` list including new tokens
3. On reconnect, the SDK gets fresh `book` snapshots for all subscribed assets
4. Brief sub-second gap during reconnect — acceptable since we get full snapshots immediately after

**SDK `OrderBookSnapshot` → our event model:**
The SDK provides `OrderBookSnapshot` from `subscribe_orderbook()`. This stream gives us the `book` snapshot events.
For other event types (price_change, last_trade_price, etc.), we need `subscribe_prices()` as well.

Actually, re-reading the reference:
- `subscribe_orderbook()` → yields `book` events (full bid/ask snapshots)
- `subscribe_prices()` → yields `price_change` events (level deltas)
- There's NO single stream in the SDK that yields ALL event types

**Revised approach:**
- Call BOTH `subscribe_orderbook(asset_ids)` and `subscribe_prices(asset_ids)`
- Merge the two streams into one using `tokio::select!` or `futures::stream::select`
- Forward each event to `event_handler`

Alternatively, for the deepest collection, we should also capture:
- `subscribe_midpoints()` for midpoint updates
- `last_trade_price` events — are they in `subscribe_prices()`? Need to verify.

Per the SDK module map in rust-sdk.md:
- `subscribe_orderbook()` → book snapshots
- `subscribe_prices()` → price change events
- `subscribe_midpoints()` → calculated midpoint prices

And per the raw WS protocol (websockets.md), the WebSocket emits `last_trade_price`, `tick_size_change`, `best_bid_ask`, `new_market`, `market_resolved` as separate event_types on the same market channel.

**The SDK may emit these additional event types on the same stream.** Let me check more carefully...

Looking at the raw protocol: ALL events on the market channel have an `event_type` field. The subscribe message is the same for all. So when you subscribe with `assets_ids`, the server sends ALL event types for those assets over a single WebSocket connection.

The SDK's `subscribe_orderbook()` returns a `Stream<OrderBookSnapshot>` which is probably filtered to just `book` events. `subscribe_prices()` returns `Stream<PriceChange>` filtered to `price_change` events.

For our use case, we need ALL events. We have two options:
1. Call multiple subscribe methods and merge streams
2. Use tokio-tungstenite directly for full control

**Decision: Use the SDK's two streams (`subscribe_orderbook` + `subscribe_prices`) merged together.** This covers `book`, `price_change`, and likely `last_trade_price`/`best_bid_ask` on the prices stream. We'll verify exact event types when implementing.

For `new_market` and `market_resolved` events — these require `custom_feature_enabled: true` in the subscription. We need to check if the SDK supports this. If not, we may need to handle these via periodic Gamma API polling instead.

Actually, according to the websockets.md reference:
- `custom_feature_enabled: true` is required for `best_bid_ask`, `new_market`, and `market_resolved`
- The SDK might or might not set this flag

**Fallback for `market_resolved`:**
If the SDK doesn't emit `market_resolved`, we can poll the Gamma API for market resolution status:
- Periodically check markets where `end_date` has passed
- Query `GET /markets/slug/{slug}` and check if `closed: true`
- The Gamma API response should indicate the winning outcome
- Alternatively, use the Data API `GET /markets/{condition_id}` for resolution info

### 3. `phase2/event_handler.rs` — Event Dispatcher

Processes each event from the WS stream:

| Event Type | Action |
|---|---|
| `book` | Insert into `orderbook_events`, update `new_markets.last_book_hash` |
| `price_change` | Insert into `orderbook_events` |
| `last_trade_price` | Insert into `orderbook_events`, update `new_markets.last_trade_price` |
| `best_bid_ask` | Insert into `orderbook_events`, update `new_markets.best_bid/best_ask` |
| `tick_size_change` | Insert into `orderbook_events` |
| `market_resolved` | Insert into `orderbook_events`, set `new_markets.winning_outcome`, `status='completed'`, `resolution_time` |

Uses `orderbook_repo` for all DB writes.

**Buffer for write throughput:**
To avoid DB write contention, batch inserts using a channel:
- `tokio::sync::mpsc::channel(buffer=10000)`
- Spawn a dedicated writer task that drains the channel and does batch INSERTs
- This prevents backpressure on the WS stream

### 5. `main.rs` — Integration

Spawn Phase 2 tasks alongside Phase 1:

```rust
#[tokio::main]
async fn main() -> Result<()> {
    // ... existing setup ...

    let pool = db::create_pool(&config.database_url).await?;

    // Spawn Phase 2 WebSocket manager as a separate task
    let ws_pool = pool.clone();
    let ws_config = config.clone();
    tokio::spawn(async move {
        loop {
            if let Err(e) = phase2::ws_manager::run_ws(ws_pool.clone(), &ws_config).await {
                error!(error = %e, "Phase 2 WS manager failed, restarting in 5s");
                tokio::time::sleep(Duration::from_secs(5)).await;
            }
        }
    });

    // Spawn Phase 2 lifecycle manager (status transitions + price_to_beat)
    let lc_pool = pool.clone();
    tokio::spawn(async move {
        let mut interval = tokio::time::interval(Duration::from_secs(5));
        loop {
            interval.tick().await;
            if let Err(e) = phase2::lifecycle::refresh_all(lc_pool.clone()).await {
                error!(error = %e, "Phase 2 lifecycle refresh failed");
            }
        }
    });

    // Phase 1 continues: existing scanner loop
    // ...
}
```

```
    Gamma API       │  upcoming    │  start_date > now()
    discovers ─────►│              │
                    └──────┬───────┘

                    ┌──────────────┐

                    └──────────────┘
```

## `price_to_beat` Computation

For each market when it transitions to `active`:
1. Get `symbol` and `start_date` from `new_markets`
2. Map to chainlink symbol: `btc` → `btc/usd`, `eth` → `eth/usd`, etc.
3. Convert `start_date` (DateTime<Utc>) to unix milliseconds for chainlink timestamp
4. Query `chainlink_prices` for the price closest to `start_date`:
   ```sql
   SELECT price FROM chainlink_prices
   WHERE symbol = $1
     AND ABS(timestamp - $2) < 60000   -- within 60 seconds
   ORDER BY ABS(timestamp - $2) ASC
   LIMIT 1
   ```
5. Store in `new_markets.price_to_beat`

This is computed ONCE when the market goes active, not on every scan.

---

## Gap Detection & Data Integrity

Track `last_book_hash` for each market. On each `book` event:
1. Compare the event's `hash` with the previous hash
2. If they don't chain (there's a gap), log a warning and request a resnapshot via REST:
   `GET https://clob.polymarket.com/book?token_id={token_id}`
3. Store the REST-fetched snapshot as a `book` event with `event_type = 'book_rest_fallback'`

This ensures we never miss orderbook state even during brief disconnections.

---

## Resolution Detection (if SDK doesn't emit `market_resolved`)

Poll Gamma API for completed markets every 60 seconds:
1. Query `SELECT * FROM new_markets WHERE status = 'active' AND end_date <= now()`
2. For each, fetch `GET https://gamma-api.polymarket.com/markets/slug/{slug}`
3. If `closed == true`, determine winner from the Gamma response
4. Update `winning_outcome` and `status = 'completed'`

## Risk & Mitigations

| Risk | Mitigation |
|---|---|
| WS disconnect causes data loss | SDK handles reconnection; gap detection + REST resnapshot fallback |
| DB write latency blocks WS stream | mpsc channel buffer + batch inserts in dedicated task |
| New market appears mid-stream | Periodic watch-list refresh + reconnect with updated asset_ids |
| chainlink_prices missing for a timestamp | 60-second tolerance window; if still missing, leave `price_to_beat` NULL |
| SDK doesn't expose `market_resolved` | Fallback to Gamma API polling every 60s |
| 7×4×2 = 56 token IDs → too many subscriptions | Market WS channel has no known subscription limit; we subscribe to both Yes+No for active+soon markets (~20-30 tokens max at once) |
