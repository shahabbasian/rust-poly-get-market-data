# Phase 2: Real-time Orderbook Collection for Live Crypto Up/Down Markets

## Context

Phase 1 (`polymarket-scanner`) discovers 7 crypto × 4 intervals = 28 Up/Down markets
per cycle, stores them in `new_markets` (token IDs, slug, start/end dates, Gamma
metadata). Phase 2 must, for every market whose window is **about to start**, connect
to the Polymarket CLOB market WebSocket, capture the full L2 orderbook stream
(`book` snapshot + every `price_change` delta) for the entire market lifetime,
record the final resolution, and store the strike price (price-to-beat) at the
market's `start_date`.

Two clarifications were already settled with the user:
- WS client: official `polymarket_client_sdk_v2` SDK (`ws` + `rtds` features).
- Storage: PostgreSQL tables (snapshot + delta rows per event).
- `price_to_beat`: RTDS primary, user's `chainlink_prices` table fallback.
- Lifecycle: add `status` enum to `new_markets` (`upcoming` / `live` / `resolved`).

The user confirmed the `chainlink_prices` table schema (an external WS
collector app populates it):
```
id          int8           (PK)
timestamp   int8           (unix milliseconds)
price       numeric
symbol      varchar        (slash format, e.g. "sol/usd")
created_at  timestamptz
```
Important: `timestamp` is **unix milliseconds** (not timestamptz), and `symbol`
uses the **slash format** (`btc/usd`, `eth/usd`, ...) which matches the
RTDS `crypto_prices_chainlink` topic exactly. This means:
- Fallback SQL must convert with `to_timestamp(timestamp / 1000.0)`.
- All 7 user assets are addressable through either RTDS chainlink (btc/eth/sol/xrp)
  or the local `chainlink_prices` table (all 7, including doge/hype/bnb).

## Database schema changes (new migration `002_phase2.sql`)

```sql
-- 1. Lifecycle status on the existing new_markets table
ALTER TABLE new_markets
    ADD COLUMN IF NOT EXISTS status         VARCHAR(16) NOT NULL DEFAULT 'upcoming',
    ADD COLUMN IF NOT EXISTS live_started_at TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS resolved_at    TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS winning_outcome TEXT,                 -- "Yes" / "No"
    ADD COLUMN IF NOT EXISTS price_to_beat   DOUBLE PRECISION,
    ADD COLUMN IF NOT EXISTS price_source    VARCHAR(32),           -- "rtds_binance" / "rtds_chainlink" / "chainlink_prices_table"
    ADD COLUMN IF NOT EXISTS collector_task_id UUID;

CREATE INDEX IF NOT EXISTS idx_new_markets_status_start
    ON new_markets (status, start_date);

-- 2. Full orderbook snapshot (one per "book" event)
CREATE TABLE IF NOT EXISTS orderbook_snapshots (
    id           BIGSERIAL PRIMARY KEY,
    market_id    UUID        NOT NULL REFERENCES new_markets(id) ON DELETE CASCADE,
    asset_id     VARCHAR(128) NOT NULL,                             -- Yes or No token
    side         VARCHAR(4)   NOT NULL CHECK (side IN ('yes','no')),
    bids         JSONB        NOT NULL,                             -- [[price,size], ...] sorted desc
    asks         JSONB        NOT NULL,                             -- [[price,size], ...] sorted asc
    hash         VARCHAR(128),
    ts_exchange  TIMESTAMPTZ,
    ts_received  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_snapshots_market_ts
    ON orderbook_snapshots (market_id, ts_received);

-- 3. Orderbook delta (one per "price_change" event row)
CREATE TABLE IF NOT EXISTS orderbook_deltas (
    id           BIGSERIAL PRIMARY KEY,
    market_id    UUID        NOT NULL REFERENCES new_markets(id) ON DELETE CASCADE,
    asset_id     VARCHAR(128) NOT NULL,
    side         VARCHAR(4)   NOT NULL CHECK (side IN ('yes','no')),
    price        DOUBLE PRECISION NOT NULL,
    new_size     DOUBLE PRECISION NOT NULL,                         -- 0 = level removed
    best_bid     DOUBLE PRECISION,
    best_ask     DOUBLE PRECISION,
    hash         VARCHAR(128),
    ts_exchange  TIMESTAMPTZ,
    ts_received  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_deltas_market_ts
    ON orderbook_deltas (market_id, ts_received);

-- 4. Trade tape (optional but cheap and high-signal)
CREATE TABLE IF NOT EXISTS orderbook_trades (
    id            BIGSERIAL PRIMARY KEY,
    market_id     UUID        NOT NULL REFERENCES new_markets(id) ON DELETE CASCADE,
    asset_id      VARCHAR(128) NOT NULL,
    side          VARCHAR(4)   NOT NULL,
    price         DOUBLE PRECISION NOT NULL,
    size          DOUBLE PRECISION NOT NULL,
    fee_rate_bps  INTEGER,
    ts_exchange   TIMESTAMPTZ,
    ts_received   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_trades_market_ts
    ON orderbook_trades (market_id, ts_received);

-- 5. Price-sampler audit log
CREATE TABLE IF NOT EXISTS strike_price_attempts (
    id           BIGSERIAL PRIMARY KEY,
    market_id    UUID        NOT NULL REFERENCES new_markets(id) ON DELETE CASCADE,
    attempted_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    source       VARCHAR(32),                                       -- rtds_binance / rtds_chainlink / chainlink_prices
    success      BOOLEAN     NOT NULL,
    price        DOUBLE PRECISION,
    note         TEXT
);
CREATE INDEX IF NOT EXISTS idx_strike_attempts_market
    ON strike_price_attempts (market_id, attempted_at DESC);
```

**Throughput note:** with 28 markets × ~5–50 events/sec (1Hz updates + burst
deltas) ≈ 200–1500 inserts/sec at peak. The collector batches inserts with a
`tokio::time::interval` flush (default 250 ms, max 1000 rows per batch) using
`UNNEST` array binds to keep latency low.

## Detailed behavior

### 1. Scheduler (`collector/src/bin/collector.rs` + `scheduler.rs`)

- Every **1 s**, query:
  ```sql
  SELECT id, symbol, interval, condition_id, token_id_yes, token_id_no,
         start_date, end_date
  FROM new_markets
  WHERE status = 'upcoming'
    AND start_date <= now() + INTERVAL '5 seconds'
  ORDER BY start_date ASC
  ```
- For each row: claim it (`UPDATE ... SET status='live', live_started_at=now(),
  collector_task_id=$taskId WHERE id=$1 AND status='upcoming'` — uses affected
  row count as a lock), then spawn a `ws_task` for **both** token IDs (Yes + No).
- Keep a `DashMap<Uuid, JoinHandle>` in memory; on shutdown, await all.
- Every 5 s, also query `resolved` candidates:
  ```sql
  SELECT id FROM new_markets
  WHERE status = 'live' AND end_date <= now() - INTERVAL '30 seconds'
  ```
  and tear down their WS tasks (defensive: market is past end, the
  `market_resolved` event should already have done this).

### 2. Per-market WS task (`ws_task.rs`)

Uses `polymarket_client_sdk_v2::clob::ws::Client`:

```rust
let mut client = ws::Client::new(PUBLIC_HOST).await?;
client.subscribe_orderbook(&[yes_token, no_token], /* custom_feature_enabled */ true).await?;
// stream events until market_resolved or end_date + 30s
while let Some(evt) = client.next().await {
    match evt.event_type {
        EventType::Book            => event_router::on_book(pool, &row, &evt).await?,
        EventType::PriceChange     => event_router::on_price_change(pool, &row, &evt).await?,
        EventType::LastTradePrice  => event_router::on_trade(pool, &row, &evt).await?,
        EventType::MarketResolved  => {
            event_router::on_resolved(pool, &row, &evt).await?;
            break;
        }
        _ => {}
    }
}
```

The SDK handles **PING every 10 s** and reconnection internally. We layer our
own bookkeeping on top: any reconnect triggers a force-flush of the
batch_writer and inserts a `strike_price_attempts`-style audit row noting the
reconnect (same table, different `note`).

**WS connection accounting:** the `polymarket_client_sdk_v2` `clob::ws::Client`
is `Clone` and shares a single `ConnectionManager` per `ChannelType` (see
`get_or_create_channel`). That means each spawned `ws_task` opens **exactly
one** underlying WebSocket to `wss://ws-subscriptions-clob.polymarket.com/ws/market`
and multiplexes all four `subscribe_*` streams (book / prices / last_trade_price /
market_resolutions) over it. With 28 live markets the peak parallel WS count to
the CLOB market channel is therefore **28 connections** (not 28×4=112). On
the RTDS side the same is true: one `RtdsClient` → one connection to
`wss://ws-live-data.polymarket.com`, regardless of how many `subscribe_*`
streams we open.

### 3. Event router (`event_router.rs`) — only the parts that matter

- `on_book`: queue `(market_id, asset_id, side, bids, asks, hash, ts)` into the
  batch writer. **Side** is derived: token_id == `row.token_id_yes` → `'yes'`,
  else `'no'`.
- `on_price_change`: one row per element in `price_changes[]`. Each row carries
  the asset's `side` (lookup against `row.token_id_yes` / `token_id_no`).
- `on_trade`: insert a `orderbook_trades` row.
- `on_resolved`: `UPDATE new_markets SET status='resolved', resolved_at=now(),
  winning_outcome=$side WHERE id=$1`; the row's `winning_asset_id` from the
  WS payload is compared with `row.token_id_yes` to determine "Yes"/"No".

All handlers are **non-blocking on DB** — they push to an in-memory bounded
channel; the `batch_writer` task drains it.

### 4. Batch writer (`batch_writer.rs`)

Single task per collector process. Holds three `Vec<Row>` buffers
(snapshots/deltas/trades) and flushes when either:
- 250 ms elapsed since last flush, **or**
- 1000 rows accumulated in any buffer.

Flush uses `sqlx::query` with `UNNEST` array binds — single round trip per
table per flush.

### 5. Price sampler (`price_sampler/src/bin/price_sampler.rs`)

Two-phase per market:

**Phase A — pre-load (5 s before `start_date`):**
- Open one RTDS connection:
  ```json
  {
    "action": "subscribe",
    "subscriptions": [
      {"topic":"crypto_prices",         "type":"*", "filters": json_filter_binance(symbol)},
      {"topic":"crypto_prices_chainlink","type":"*", "filters": json_filter_chainlink(symbol)}
    ]
  }
  ```
  RTDS symbol mapping (only Binance and Chainlink topics are supported on RTDS;
  the slash-format `chainlink_prices` table is the local fallback that covers
  **all 7 assets**):
  | crypto | Binance       | Chainlink RTDS     | chainlink_prices table |
  |--------|---------------|--------------------|------------------------|
  | btc    | btcusdt       | btc/usd            | btc/usd                |
  | eth    | ethusdt       | eth/usd            | eth/usd                |
  | sol    | solusdt       | sol/usd            | sol/usd                |
  | xrp    | xrpusdt       | xrp/usd            | xrp/usd                |
  | doge   | — (no topic)  | — (no topic)       | doge/usd               |
  | hype   | — (no topic)  | — (no topic)       | hype/usd               |
  | bnb    | — (no topic)  | — (no topic)       | bnb/usd                |

  Doge/hype/bnb have no RTDS topic at all → skip RTDS subscription for them
  and go straight to the `chainlink_prices` table fallback.

- Keep a `BTreeMap<i64, (f64, f64)>` of `(exchange_ts_ms -> (binance, chainlink))`
  per symbol, ring-buffered to last 5 minutes (low memory).

**Phase B — at `start_date`:**
- Try Chainlink first (Polymarket resolves against Chainlink), then Binance.
- For doge/hype/bnb: skip RTDS, go directly to fallback.
- If neither RTDS source has a tick within ±2 s of `start_date`, fallback to
  the user's `chainlink_prices` table. The `timestamp` column is unix ms, so:
  ```sql
  SELECT price,
         to_timestamp(timestamp / 1000.0) AS ts
  FROM chainlink_prices
  WHERE symbol = $1                                         -- e.g. 'doge/usd'
    AND timestamp >= ($2::bigint) - 2000                    -- ±2s in ms
    AND timestamp <= ($2::bigint) + 2000
  ORDER BY abs(timestamp - $2::bigint) ASC
  LIMIT 1
  ```
  (where `$2` is `extract(epoch from start_date) * 1000`).
- Persist: `UPDATE new_markets SET price_to_beat=$1, price_source=$2 WHERE id=$3`,
  insert a `strike_price_attempts` row regardless of success.
- For markets that already have a `price_to_beat` set, do nothing (idempotent
  re-runs after restarts).

**One RTDS connection per process** is enough — RTDS streams all 4 supported
symbols on a single subscription. The process keeps a `HashMap<MarketId,
oneshot::Sender<PriceTick>>` of "I'm waiting for the strike for this market";
incoming ticks route to the right waiter if their `exchange_ts` is within ±2 s
of a registered `start_date`, otherwise they just refresh the ring buffer.

### 6. Status transitions (`status.rs`)

```
upcoming ──(start_date reached, WS subscribed)──► live
live     ──(market_resolved event OR end_date+30s)──► resolved
```

`collector` owns `upcoming → live` and `live → resolved`.
`price_sampler` reads `status` to know which markets to arm but does not
mutate it.

## Risks / open questions

1. **Confirmed chainlink_prices schema**: `(id int8, timestamp int8 [unix ms],
   price numeric, symbol varchar [slash format], created_at timestamptz)`. Confirmed
   all 7 user assets are written to it in slash format, so the fallback works
   uniformly. **Confirm the exact symbol strings** for doge/hype/bnb (likely
   `doge/usd`, `hype/usd`, `bnb/usd`) by spot-checking the table once before
   wiring the fallback SQL.
2. **SDK pin**: verify the latest `polymarket_client_sdk_v2` version with
   `cargo search polymarket_client_sdk_v2` before committing. The exact `ws::Client`
   method names (`subscribe_orderbook`, `next()`, `EventType` enum variants)
   are taken from the skill's `references/rust-sdk.md` and `websockets.md` and
   should be cross-checked against the pinned source on first build.
3. **RTDS gap window**: if the WS drops and reconnects in the ±2 s window
   around `start_date`, we could miss the strike. Mitigation: 30 s of ring
   buffer history + immediate fallback to `chainlink_prices` table. We
   persist all attempts to `strike_price_attempts` so we can audit missing
   strikes.
4. **Reconnect safety**: on WS reconnect we re-subscribe and rely on the
   next `book` snapshot to resync. `price_change` deltas between the
   reconnect and the new snapshot are discarded (we never apply a delta
   without a baseline). This is acceptable per the websockets reference
   "don't trust stale deltas" guidance.
5. **Lifecycle label overhead**: adding `status` requires an extra
   `idx_new_markets_status_start` and one UPDATE per state change. Negligible
   at our scale (28 markets/cycle).
6. **3 of 7 assets have no RTDS coverage** (doge, hype, bnb). They rely
   entirely on the `chainlink_prices` table fallback. Verified above that
   the table uses the same slash format, so the fallback path is
   straightforward.

## Out of scope: Redis

We deliberately **do not** introduce Redis (or any other in-memory cache /
pub-sub broker) in Phase 2. All data flows directly from the WebSocket
ingest path to PostgreSQL. The reasons:

- **Single source of truth.** Every byte Phase 2 produces (snapshots, deltas,
  trades, strike attempts) is durable in `orderbook_*` and
  `strike_price_attempts` the moment it is written. A reader / replay tool can
  reconstruct the full L2 tape by replaying the rows in
  `(market_id, ts_received)` order — no warm cache required, no
  cache-vs-DB divergence to debug.
- **Throughput is well within Postgres.** At the projected 28 markets ×
  ~5–50 events/sec peak we expect ≤1.5k rows/sec. The `batch_writer` already
  coalesces into UNNEST-array INSERTs, which is the same pattern Postgres
  itself uses internally for high-throughput WAL inserts.
- **No cross-process coordination requirement.** The scheduler claims rows
  atomically with `UPDATE ... WHERE status='upcoming'` and uses the affected
  row count as a lock. The price-sampler is a single process that owns one
  RTDS connection; no other consumer needs to subscribe to its events.
- **Failure mode is simpler.** When a Redis pod dies, the system has to
  decide between stale-cache risk and a full DB re-read on cold start. With
  Postgres as the only hot path, "restart" simply means "resume from the
  last `resolved` row".
- **Operational footprint stays tiny.** Phase 1's `docker-compose.yml` is
  three containers (scanner + postgres + supabase-net). Adding Redis would
  mean a fourth container, a second volume, a password/ACL to manage, and
  a second failure domain — all to solve a problem (low-latency fan-out)
  that the consumer side can solve with `LISTEN/NOTIFY` or by polling
  `new_markets` directly if it ever actually materializes.

If a future phase genuinely needs sub-millisecond pub-sub (e.g. a live
dashboard driven by per-event deltas), the right place to introduce it is
**after** the batch_writer flush, as a *secondary* sink that mirrors a
filtered subset of events — not as a primary write path that the WS tasks
must reach before persisting.
